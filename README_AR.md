# نموذج طبقة البيانات وطابور المهام لمنصة OSINT

## ما الذي يوضحه النموذج؟
- PostgreSQL لتخزين مهام الفحص والنتائج ومصدر كل نتيجة وتوقيتها.
- Redis كطابور لتسليم أرقام المهام إلى الـ Worker.
- فصل حساب قاعدة البيانات الخاص بالـ Backend عن حساب الـ Worker.
- التحقق من صيغة النطاق باستخدام Python parameterized queries لتجنب SQL injection.
- ربط كل مهمة بمعرّف مالك، والتحقق من الملكية عند عرض النتائج.

**تنبيه:** هذا نموذج تعليمي محلي. الـ Worker لا يتصل بالإنترنت ولا يجري فحصًا حقيقيًا؛ النتائج تجريبية فقط. لا تستخدم أي OSINT إلا على نطاقات لديك تصريح بفحصها.

## المتطلبات
- Docker Desktop
- Python 3.10 أو أحدث

## التشغيل على Windows PowerShell
1. فك ضغط المشروع وافتح PowerShell داخل المجلد.
2. شغّل الخدمات:

   `docker compose up -d`

3. أنشئ بيئة Python افتراضية وثبّت المكتبات:

   `py -m venv .venv`

   `.\.venv\Scripts\Activate.ps1`

   `pip install -r requirements.txt`

4. انسخ `.env.example` إلى `.env`، ثم حمّل متغيراته في نافذة PowerShell الحالية (بعد تعديل كلمات المرور لتطابق إعدادات الخدمات):

   `$env:BACKEND_DATABASE_URL="postgresql://backend_app:change_backend_password@127.0.0.1:5432/osint_db"`

   `$env:WORKER_DATABASE_URL="postgresql://worker_app:change_worker_password@127.0.0.1:5432/osint_db"`

   `$env:REDIS_URL="redis://:change_this_redis_password@127.0.0.1:6379/0"`

   هذه كلمات مرور تجريبية للتوضيح فقط. غيّرها قبل أي استخدام حقيقي، وغيّرها أيضًا داخل `docker-compose.yml` و`schema.sql` قبل أول تشغيل. تهيئة `schema.sql` تعمل تلقائيًا فقط عند إنشاء مجلد بيانات PostgreSQL لأول مرة.

5. أنشئ مهمة تجريبية:

   `python app.py create --owner student1 --domain example.com`

6. شغّل العامل لمعالجة مهمة واحدة:

   `python app.py work`

7. اعرض النتائج:

   `python app.py results --owner student1 --task-id 1`

   استبدل `1` برقم المهمة الذي ظهر عند إنشائها.

## ملفات المشروع
- `docker-compose.yml`: يشغّل PostgreSQL وRedis محليًا.
- `schema.sql`: ينشئ الجداول والفهارس وحسابات قاعدة البيانات وصلاحياتها.
- `app.py`: إنشاء المهام، وضعها بالطابور، معالجة مهمة تجريبية، وعرض النتائج.
- `requirements.txt`: مكتبات Python المطلوبة.
- `.env.example`: نموذج متغيرات الاتصال؛ لا تضع أسرارًا حقيقية في Git.

## ملاحظات أمنية وحدود النموذج
1. ربط المنافذ بـ `127.0.0.1` يقلل تعرض الخدمات للشبكة، لكنه ليس بديلًا عن إعدادات firewall أو تأمين Docker.
2. كلمات المرور في الملفات الحالية تجريبية. في الإنتاج استخدم أسرارًا قوية وخزنة أسرار، ولا ترفع الأسرار إلى Git.
3. Redis list هنا نموذج مبسّط؛ قد تضيع مهمة من الطابور إذا توقف العامل بعد سحبها. في الإنتاج استخدم Redis Streams مع consumer groups أو RabbitMQ مع acknowledgements وإعادة المحاولة.
4. إنشاء سجل المهمة ثم إضافته إلى Redis ليس عملية ذرية واحدة؛ قد يُنشأ سجل دون وصوله للطابور. في الإنتاج استخدم Transactional Outbox أو نمطًا مكافئًا.
5. `owner_id` هنا للتوضيح فقط وليس مصادقة حقيقية. اربطه بهوية موثّقة من الـ Backend/JWT، ولا تثق بقيمة يرسلها العميل وحده.
6. `error_message` في هذا المثال مبسّط؛ في الإنتاج لا تعرض تفاصيل داخلية أو أسرارًا للمستخدم.
7. تشفير القرص/النسخ الاحتياطية، تدوير الأسرار، مراقبة السجلات، واختبارات الاستعادة مطلوبة قبل النشر الحقيقي.
